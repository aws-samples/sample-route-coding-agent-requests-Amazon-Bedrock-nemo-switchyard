# Security Policy

## Reporting a Vulnerability

If you discover a potential security issue in this project, we ask that you
notify AWS Security via our
[vulnerability reporting page](https://aws.amazon.com/security/vulnerability-reporting/)
or directly via email to aws-security@amazon.com.

**Please do not create a public GitHub issue for security vulnerabilities.**

## Scope and Intent

This repository contains **sample code**. It shows how to run the NVIDIA Switchyard routing plugin
inside a LiteLLM gateway for Amazon Bedrock on Amazon ECS with AWS Fargate.
It is meant for learning and as a starting point, not as a drop-in production
system. This is sample code, for non-production usage. You should work with
your security and legal teams to meet your organizational security, regulatory
and compliance requirements before deployment. Don't deploy it to production
without additional security testing.

Before deploying any part of this sample into your own environment, review it
against your organization's security requirements. In particular:

- **Network exposure.** The load balancer only accepts traffic from the CIDR
  range you pass as `allowedCidr`. The code rejects `0.0.0.0/0` at synth time.
  The allowlist works at the network level only: everyone behind an allowed
  address can reach the endpoint, so use your own `/32`.
- **HTTPS by default.** Synth fails unless you pass `domainName` with either
  `hostedZone` (CDK creates the ACM certificate and the alias record) or
  `certificateArn` (an existing ACM certificate), or opt in to plain HTTP with
  `-c allowPlainHttp=true`. With the opt-in, the listener serves plain HTTP on
  the load balancer's DNS name, and CDK prints a synth warning that says so.
  The master key (the `Authorization` header), prompts, tool results and
  source code, and model responses then cross the network unencrypted between
  the client and the load balancer, where anyone on the path can read or
  change them. Use the opt-in only for a short test with non-sensitive code
  from your own `/32`, then rotate the key, and run `cdk destroy` when you
  finish.
- **Secrets.** The LiteLLM master key is generated by AWS Secrets Manager and
  injected into the container at start. It is never written into a template,
  a configuration file, or this repository. Rotate it after testing. Every key
  holder is a gateway administrator with no spend cap, so create an AWS Budgets
  alert for Amazon Bedrock before deploying.
- **AWS WAF.** The web ACL keeps no sampled requests, because each sample
  would store every request header, including the master key, for three
  hours. CloudWatch metrics stay on. If you add AWS WAF logging, redact the
  `authorization` header.
- **IAM.** The task role may call `bedrock:InvokeModel` and
  `bedrock:InvokeModelWithResponseStream` for the models in the selected
  profile’s `litellm.yaml`. For a cross-Region inference profile, the
  foundation-model resource has a `*` Region and a trailing `*`, so it also
  matches any other model ID with the same prefix, and it is not conditioned
  on the inference profile ARN. The sample accepts this as a Low finding. To
  narrow it, add the `bedrock:InferenceProfileArn` conditions shown in
  [Global cross-Region inference](https://docs.aws.amazon.com/bedrock/latest/userguide/global-cross-region-inference.html).
  Review the derived policy before deploying.
- **Routing.** LiteLLM validates the gateway key and invokes the Switchyard
  plugin. The load balancer targets LiteLLM in private subnets. Its security
  group limits task access to the load balancer.
- **Data.** Prompts and completions pass through LiteLLM and the selected
  Bedrock model. The coding demo saves model messages, tool results, and code
  in its local results directory. Protect those artifacts as workload data.
- **Coding demo.** The runner executes model-written Python. It removes AWS
  credentials from the subprocess environment and runs the tests on a
  temporary copy of the workspace with `HOME` set to that copy, which is not a
  sandbox. Use a disposable environment where no long-lived AWS credentials
  are on disk, and review the generated code before reusing it.

## Known limitations

The sample accepts these items as they are. Each one is documented here instead
of being changed in code:

- **Wide `allowedCidr` ranges.** The stack rejects only world-open ranges and
  accepts any narrower IPv4 CIDR. Use your own `/32`.
- **Port 80 in HTTPS mode.** With a domain, port 80 stays open to redirect to
  HTTPS. A client configured with `http://` sends its key before the redirect,
  so always use the `https://` URL.
- **No sandbox for the coding demo.** The runner executes model-written Python
  as your user, with your file-system and network access, outside any
  container or operating-system sandbox.
- **Builder-stage maturin pin.** The image's builder stage installs maturin
  from PyPI by version, without a hash. That stage is discarded and does not
  ship.
- **No image scan in CI.** CI builds the gateway image but doesn't scan it,
  and Dependabot doesn't update the LiteLLM base image.
  [Design decisions](docs/DECISIONS.md) describes the manual upgrade and a
  local scan.
- **Base images outside Amazon ECR Public.** LiteLLM publishes its image only
  on the GitHub Container Registry, and the Dockerfile frontend comes from
  Docker Hub. Both are pinned by digest, so a moved tag can't change the build.
- **Unpatched CVEs in the LiteLLM base image.** The build installs the fixed
  releases that exist for the base image's vulnerable packages and removes
  Node.js and ddtrace. Vulnerabilities without a usable fixed release, and
  lower-severity ones that the patch list doesn't cover, stay until the base
  image moves. Scan the image before you deploy.
- **Placeholder key in `.env.example`.** Compose runs with `sk-REPLACE-ME` if
  you copy the file and don't export your own key. Compose publishes the port
  on `127.0.0.1` only.
- **Credentials in custom profiles.** Validation doesn't reject credentials in
  a profile's `litellm_params`. Never put them there: the profile text goes
  into the task definition and the template in plain text. Validation does
  reject the two LiteLLM settings that turn its request-body guard off,
  `allow_client_side_credentials` and `configurable_clientside_auth_params`,
  and the gateway plugin rejects a request that carries its own `api_key`,
  AWS keys, or an `Authorization` header in `extra_headers`, `headers` or
  `provider_specific_header`, anywhere in the body (fallback targets
  included), with HTTP 400, so every call runs under the task role.
- **LiteLLM log content.** Whether LiteLLM writes prompt content to CloudWatch
  at `LITELLM_LOG=INFO` (30-day retention) hasn't been checked. Treat the log
  group as workload data.
- **Key on command lines.** The README's commands pass the key on command lines
  and keep it in your shell's environment. Use a single-user machine, and
  rotate the key when you finish.
- **Path allowlist edge cases.** The load balancer's path allowlist hasn't been
  tested with dot-segment, percent-encoded, or mixed-case paths.
- **Version ranges in `package.json`.** `npm ci` installs the exact versions and
  integrity hashes in `package-lock.json`. Use it instead of `npm install`.
- **Bedrock grant precision (Low).** The cross-Region foundation-model grant is
  broader than one model ID. See **IAM** above.
- **PyO3 0.28 in the Switchyard extension.** Switchyard's manifests pin PyO3
  0.28.3, which has GHSA-36hh-v3qg-5jq4 and GHSA-chgr-c6px-7xpp (fixed in
  0.29.0). The extension doesn't call the affected APIs (`nth` and `nth_back`
  on list and tuple iterators, and `PyCFunction::new_closure`). The image build
  moves the other crates with advisories to fixed releases.

See the [README](README.md) for the full list of guardrails, and its
[Before production](README.md#before-production) list for the hardening this
sample leaves out.
